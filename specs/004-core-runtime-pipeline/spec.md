# Feature Specification: 核心运行时与消息管道（迁移阶段 0、1）

**Feature Branch**: `004-core-runtime-pipeline`

**Created**: 2026-08-08

**Status**: Draft

**Input**: User description: "我预期让你执行Bai/Scriptor_to_Bai_migration/migration-plan.md中的阶段0和1."

## Scope

### In Scope

- 阶段 0：核对并确认两处清单标记已经落盘——远程编码代理接入归入未来插件系统；内置技能暂缓、只做技能框架。两处已落实，本阶段不产生代码改动，仅记录核对结果。
- 阶段 1 核心运行时：对话消息、定时事件、系统事件统一进入同一个串行消息处理管道（不引入事件总线）；后台异步任务具备提交、串行执行与状态查看能力（最小执行器，不做优先级/取消/持久化）；同一会话防重入（同一时刻只处理一个对话动作，新输入等待）。
- 阶段 1 配置管理：配置分组管理、启动时与运行中合法性校验、运行中修改配置无需重启即可生效。
- 阶段 1 生命周期：正常启动/停止、资源清理、优雅退出，不破坏既有原始记录与长期记忆。
- 阶段 1 可观测性：可查看当前会话、队列、任务与健康度等运行状态和统计信息。
- 阶段 1 消息体验：一次输入动作（一次粘贴的多行或一次管道输入）合并为一条对话动作处理，避免被拆成多轮回复；回复一次性完整输出，不做分段与自然停顿。
- 既有 Bai 能力全部保留并扩展：永久 raw 记录、长期记忆与来源追溯、人格/状态、工具事务协议、提示词调试 TUI、凭据门禁等不得回归。

### Out of Scope

- 阶段 2 及以后的模型生成能力（流式输出、对话压缩、轻量模型判断、定时任务自主执行）不在本规格内实现，但阶段 1 的统一事件入口须为其预留可行进路径。
- 完整定时任务调度、待办、心跳与夜间维护（阶段 7）不在本阶段实现。
- 工具系统、Agent 编排、记忆与知识统一模块、身份安全、扩展机制（阶段 3-8）不在本规格内。
- 不引入外部消息中间件、多进程/多实例或第三方 agent 平台；保持单用户、单会话、本地 CLI 的定位。
- 不做基于时间窗口的消息合并（IM 场景语义）；未来接入 IM/多输入源时按已归档的防抖合并需求另行实现。
- 不做长回复分段与"自然停顿"（IM 场景体验）；未来接入 IM 或实现流式输出时按需实现。

## Clarifications

### Session 2026-08-08

- Q: 阶段 1 的"事件驱动架构"你希望做到哪种强度？ → A: 统一消息处理管道：对话/定时/系统输入全部汇入同一个串行处理流程，带会话防重入，不引入事件总线或订阅/发布机制。
- Q: 连续消息合并在本地 CLI 下希望怎么处理？ → A: 只合并一次输入动作：一次粘贴的多行（或一次管道输入）作为一条对话动作处理，不做时间窗口合并。
- Q: 长回复分段与"自然停顿"在本地 CLI 下希望怎么处理？ → A: 本阶段不做分段与停顿，CLI 一次性输出完整回复；未来接入 IM 或流式输出时按需实现。
- Q: 阶段 1 的后台异步任务机制做到什么范围？ → A: 只做最小后台执行器：可提交后台工作、串行执行、记录状态（等待/执行/成功/失败）并提供简单查看，不做优先级、取消、持久化。
- Q: 阶段 1 的并发控制做到什么范围？ → A: 只做会话防重入：同一会话同一时刻只处理一个对话动作，新输入等待；不做并行请求限制与重要请求优先。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全天持续运行的核心会话 (Priority: P1)

作为长期使用 Bai 的用户，我希望聊天输入和各类系统事件都被统一、有序地处理，同一会话不会因快速连发或系统事件并发而重复处理或乱序，并且随时可以干净地停止程序而不丢失已完成的对话。

**Why this priority**: 统一消息处理管道、会话防重入与生命周期是整个迁移计划的地基，后续所有阶段都依赖它；没有它，其余功能无法安全叠加。

**Independent Test**: 在固定输入序列中同时注入对话消息与系统事件，验证每个输入恰好进入一次处理流程、回复不重复、顺序可观测；再在队列非空时发送停止信号，验证进程在资源清理完成后退出且既有数据完好。

**Acceptance Scenarios**:

1. **Given** 会话正在处理一条输入，**When** 用户在同一时刻再发送一条输入或系统事件到达，**Then** 新输入进入等待/合并状态而不打断当前处理，且当前轮不会被重复处理。
2. **Given** 多条对话消息与系统事件在短时间内连续到达，**When** 它们进入处理流程，**Then** 每个输入按照可观测的顺序恰好被处理一次，回复与处理结果一一对应，不重复、不丢失。
3. **Given** 有排队中的后台任务和未完成轮次，**When** 用户发出正常停止请求（例如按 Ctrl+C），**Then** 进程停止接收新工作，将未完成轮次按既有 pending 协议安全落盘、完成资源清理后优雅退出；重启后既不重发已完成的轮次，也能按既有策略恢复或丢弃 pending。

### User Story 2 - 不改配置就不必重启 (Priority: P1)

作为运行维护者，我希望修改配置后无需重启即可让新配置生效，同时在配置写错时得到明确的失败提示，并且不会让系统带着半套新旧混用的配置继续运行。

**Why this priority**: 配置热重载与合法性校验是"长跑进程"可用性的基础；强制重启会打断会话，混用配置会导致不可复现的行为。

**Independent Test**: 在进程运行中修改某配置分组的字段，验证下一轮处理立即使用新值；再写入非法配置（缺失、类型错误、越界、组间冲突），验证受影响分组保持旧值并给出可操作错误，其他分组仍正常工作。

**Acceptance Scenarios**:

1. **Given** 进程正在运行且已完成启动校验，**When** 用户修改某一配置分组中的受支持字段并保存，**Then** 无需重启，下一轮处理立即按新配置工作。
2. **Given** 配置按分组管理，**When** 某一分组配置非法，**Then** 该分组保持最后一份有效配置，启动或运行中的校验给出可操作错误（指出分组与字段），其他合法分组不受影响。
3. **Given** 一轮处理已经开始，**When** 处理过程中配置被修改，**Then** 该轮继续使用其开始时已生效的配置快照，不中途混入新值。
4. **Given** 运行中出现非法配置，**When** 修复文件后再次保存或重试，**Then** 无需重启即可恢复，且不会要求迁移既有数据。

### User Story 3 - 一次粘贴不再拆成多轮 (Priority: P1)

作为用户，我希望一次输入动作（例如一次粘贴的多行文本或一次管道输入）被当作一条对话动作处理，而不是逐行触发多轮回复。

**Why this priority**: 用户明确标记为重点体验项（[!]）；本地 CLI 下"一次动作被拆成多轮"的真实场景就是粘贴/管道多行输入，合并直接决定回复质量。

**Independent Test**: 一次粘贴或管道输入多行内容，验证整体作为一条对话动作处理且只产生一次回复；再验证交互式逐行输入时每行仍作为独立动作处理。

**Acceptance Scenarios**:

1. **Given** 用户一次粘贴多行文本或通过管道输入多行，**When** 它们进入处理流程，**Then** 整体作为一条对话动作处理，只产生一次回复，回复覆盖全部内容。
2. **Given** 用户在交互终端逐行输入，**When** 每行回车提交，**Then** 每行作为独立对话动作处理，不做时间窗口合并。
3. **Given** 单次输入动作内容非常大，**When** 它到达，**Then** 作为一条对话动作处理且内容不被截断或拆分。

### User Story 4 - 后台任务看得见、排得上 (Priority: P2)

作为运行维护者，我希望耗时操作（如整理、检索、维护）作为后台任务排队执行，并能随时查看每个任务的状态，任务失败不会被静默吞掉。

**Why this priority**: 后台任务机制是后续记忆整理、夜间维护、定时任务自主执行等能力的共同底座；状态可见是运维可用性的最低要求。

**Independent Test**: 提交多个后台任务并制造一个失败任务，验证它们按提交顺序依次执行、状态可查（等待/执行/成功/失败），失败任务有明确结果与可重试信息。

**Acceptance Scenarios**:

1. **Given** 提交了多个后台任务，**When** 系统按提交顺序串行执行，**Then** 每个任务的状态（等待/执行/成功/失败）可被查询，且查询结果与实际执行一致。
2. **Given** 一个任务失败，**When** 它结束执行，**Then** 任务被标记为失败并保留可操作的原因，可重试或可被清理，不静默消失。
3. **Given** 已有任务正在执行，**When** 再提交新任务，**Then** 新任务进入等待状态并在当前任务结束后自动开始执行。

---

### User Story 5 - 系统健康一眼可知 (Priority: P3)

作为运行维护者，我希望随时查看当前会话状态、队列长度、任务情况和健康度，判断系统是否正常、是否需要干预。

**Why this priority**: 单用户常驻进程需要低成本的可观测入口；这也是迁移计划"运行状态与统计信息查看"的直接验收。

**Independent Test**: 在运行中查询状态视图，验证其中包含当前会话、队列、任务与健康度信息，且与同时发生的真实事件一致。

**Acceptance Scenarios**:

1. **Given** 系统正常运行，**When** 用户查看运行状态，**Then** 能看到当前会话、队列、任务和健康度等统计信息。
2. **Given** 有任务失败或队列堆积，**When** 用户查看运行状态，**Then** 统计信息如实反映失败与堆积，便于定位干预。
3. **Given** 会话处于 pending 恢复或等待状态，**When** 用户查看运行状态，**Then** 当前会话状态明确可见，不与其他状态混淆。

作为项目维护者，我希望阶段 0 的两处清单标记已被确认落盘，避免后续阶段建立在错误的范围假设上。

**Why this priority**: 阶段 0 是无功能条目的文档核对，但它锁定"远程编码代理"与"内置技能"的范围边界，影响阶段 8 与未来插件系统。

**Independent Test**: 对照 `feature-checklist.md` 与 `future-and-discarded.md` 中的两处条目原文，验证标记与归档状态一致。

**Acceptance Scenarios**:

1. **Given** `feature-checklist.md` 第 4 节备注与 `future-and-discarded.md` 第 4 节，**When** 核对远程编码代理接入条目，**Then** 确认其已归入未来插件系统且不在本期实现范围。
2. **Given** `feature-checklist.md` 第 12 节，**When** 核对内置技能条目，**Then** 确认其标记为暂缓（只做技能框架），未进入阶段映射。

### Edge Cases

- 一次粘贴/管道输入包含大量行或超长内容：作为单条对话动作处理，不逐行拆轮，不截断内容。
- 停止信号到达时有排队任务或未完成轮次：未完成轮次按既有 pending 协议安全落盘；已排队任务的处理结果与丢弃策略必须明确，不得损坏原始记录。
- 停止信号到达时存在正在执行的写类操作：遵循既有事务协议，失败不留半截副作用。
- 配置在保存过程中被写成半截文件或格式错误：校验必须整体失败并保持旧分组生效，不得读取部分新值。
- 多个配置分组同时修改且其中一组非法：合法分组正常生效，非法分组保持旧值，错误信息可定位到具体分组与字段。
- 同一时刻消息与定时事件同时到达：按到达顺序串行处理，不区分优先级。
- 事件处理失败后重试或再次投递：必须幂等，不得重复写入记录或产生重复回复。
- 统计查询与事件提交并发：查询返回可重复的一致快照，统计在事件完成后更新，不出现重复计数。
- 任务执行中进程退出：进行中的工作按生命周期策略安全中止并明确标记，重启后不得静默重放或损坏数据。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的消息处理管道：对话消息、定时事件与系统事件按到达顺序进入同一个串行处理流程，并按可观测的顺序处理；MUST NOT 引入事件总线或发布/订阅框架。
- **FR-002**: 系统 MUST 保证同一会话同一时刻只处理一个对话动作；处理进行中到达的新输入 MUST 进入等待状态，MUST NOT 并发处理同一会话。
- **FR-003**: 系统 MUST 在运行中修改配置后无需重启即可生效，生效时间点 MUST 为下一轮处理开始，不得中途变更进行中的轮次。
- **FR-004**: 系统 MUST 按配置分组管理配置，并在启动时与运行中执行合法性校验；任一分组非法时 MUST 保持该组最后一份有效配置并给出可操作错误。
- **FR-005**: 系统 MUST 提供最小后台执行器：任务可提交并按提交顺序串行执行，状态（等待/执行/成功/失败）可查询；MUST NOT 引入优先级、取消或持久化。
- **FR-006**: 系统 MUST 支持正常启动与停止：停止时停止接收新工作、按既有协议落盘未完成轮次、完成资源清理后优雅退出。
- **FR-007**: 系统 MUST 提供运行状态与统计信息查看，至少包含当前会话、队列、任务与健康度，且与实际状态一致。
- **FR-008**: 系统 MUST 把一次输入动作（一次粘贴的多行或一次管道输入）作为一条对话动作处理，并只产生一次回复；MUST NOT 基于时间窗口合并输入。
- **FR-009**: 阶段 0 MUST 完成两处标记核对并记录结果：远程编码代理接入归入未来插件系统；内置技能暂缓、只做技能框架。两处均已落盘，无需代码改动。

### Core Business Rules *(mandatory)*

- **BR-001**: 每个对话消息与事件 MUST 恰好被处理一次：正常路径产生唯一结果；失败路径产生明确错误；重试或重复投递 MUST NOT 产生重复回复或重复写入。可测：成功、失败、重试三种输入序列下，回复数与记录数均不重复。
- **BR-002**: 同一会话防重入 MUST 无条件成立：处理进行中到达的输入只能等待，任何并发路径都不得同时处理同一会话。可测：在固定点并发注入多条输入，验证处理串行且顺序一致。
- **BR-003**: 配置分组 MUST 原子生效：分组整体校验、整体切换；任一组非法时该组 MUST 保持旧值，其他组可正常生效；进行中的轮次 MUST 使用开始时的配置快照。可测：正常、半截文件、越界、组间冲突与轮次中修改五种场景。
- **BR-004**: 后台任务状态机 MUST 可观测且不静默丢失：状态转换只有 等待→执行→成功/失败 一条路径；失败任务 MUST 保留可操作原因并可重试或清理。可测：成功、失败、进程内积压三种场景的状态序列。
- **BR-005**: 优雅退出 MUST 不破坏数据：停止后不得接收新工作；未完成轮次按既有 pending 协议安全落盘；已完成的轮次与长期记忆 MUST NOT 被改写或删除。可测：各队列非空、pending 存在/不存在时停止，重启后数据完整。
- **BR-006**: 一次输入动作 MUST 合并为一次处理：一次粘贴/管道输入的多行整体进入同一轮，只产生一次回复；交互式逐行输入仍逐行处理，不引入时间窗口合并。可测：多行粘贴、多行管道、逐行输入三种场景。
- **BR-007**: 统计与状态 MUST 与真实状态一致：统计在事件完成后更新，查询返回一致快照，不得重复计数或显示已不存在的任务。可测：并发提交与查询下统计与日志一致。

- **DR-002**: 功能 quickstart 与运行手册（如 `specs/001-persistent-memory-agent/quickstart.md`、`docs/ubuntu-deployment.md`）MUST 同步更新启动/优雅停止、运行中改配置、状态查看与恢复验证的命令和步骤，且示例可执行。
- **DR-003**: 配置与公共契约文档（如 `specs/001-persistent-memory-agent/contracts/configuration.md`）MUST 记录配置分组、校验规则与热重载语义，并说明既有数据无需迁移。
- **DR-004**: `Scriptor_to_Bai_migration/migration-plan.md` 的阶段 0/1 验收状态 MUST 在本功能完成后更新为可核对的完成记录，并链接到本规格。
- **DR-005**: 新增或变更的 CLI 命令与配置项 MUST 在 README、quickstart 和对应契约中保持一致，并通过文档中的命令可执行性检查验证。

### Key Entities *(include if feature involves data)*

- **处理项（事件）**：进入统一消息处理管道的最小工作单元，包含对话消息、定时事件与系统事件；具有来源类型与到达顺序，经管道串行处理。
- **对话动作**：一次处理的最小单元；可能由单条输入构成，也可能由一次输入动作（一次粘贴/管道输入的多行）合并而成。
- **后台任务**：可提交、串行执行、查询状态的工作单元；状态为等待/执行/成功/失败，失败保留原因。
- **配置分组**：按领域组织的配置集合；整体校验、整体生效，保留最后有效版本作为回退。
- **会话**：单用户持续交互上下文；具有当前处理状态与防重入约束。
- **运行状态与统计**：当前会话、队列、任务与健康度的可查询快照。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 现有 CLI 全流程（config/chat/memory/doctor/security）与既有自动化回归测试全部通过，既有记忆、安全、调试能力无回归。
- **SC-002**: 一次粘贴/管道输入的多行内容在自动化验收中 100% 作为一条对话动作处理并只产生一次回复；交互式逐行输入 100% 保持逐行独立处理。
- **SC-003**: 运行中修改任意受支持配置后，无需重启即在下一轮生效；非法配置场景下受影响分组 100% 保持旧值并给出可操作错误。
- **SC-004**: 在存在排队任务与 pending 轮次时发起停止，进程完成落盘与资源清理后退出；重启后 100% 无重复轮次、无数据损坏，pending 按既有策略处理。
- **SC-005**: 任务状态查询与实际执行结果 100% 一致；失败任务全部可见且保留原因，无静默丢失。
- **SC-006**: 运行状态视图在验收场景中显示的会话、队列、任务与健康度与实际状态一致，统计无重复计数。

## Assumptions

- 保持单用户、单会话、本地 CLI 的既有定位；统一消息处理管道指进程内串行处理流，不引入事件总线、发布/订阅框架、外部消息中间件或常驻服务；阶段 8 的钩子能力后续可直接在管道上扩展。
- 阶段 1 只建立统一事件入口并支持定时事件类型的基本投递；完整定时任务调度、持久化与自主执行属于阶段 7。
- 不引入基于时间窗口的输入合并；"一次输入动作"以输入源边界（一次粘贴、一次管道输入）判定，不依赖时间阈值。
- 阶段 1 不引入并行请求限制与请求优先级：所有处理项按到达顺序串行处理；并行与优先级能力等阶段 3/4 需要时再引入。
- 阶段 0 两处标记核对无需代码改动；本规格的核对记录即阶段 0 交付物。
- 阶段 1 不得改变既有数据布局：原始记录、长期记忆与来源追溯继续兼容使用，不迁移、不改写。
