# Feature Specification: 提示词追踪调试工具

**Feature Branch**: `002-prompt-trace-debugger`

**Created**: 2026-07-19

**Status**: Draft

**Input**: User description: "增加一个调试工具：实时显示每次对话发给模型提供商的原始提示词；在界面中追踪最终提示词每一段来自哪个文件；以不同颜色和错开布局展示；显示估算的已用上下文窗口。"

## Scope

### In Scope

- 在现有终端交互流程中按需开启基础类 TUI 调试界面，并可明确确认调试状态。
- 捕获一轮交互触发的每一次模型提供商出站请求，包括聊天、记忆整理、工具结果续接及未来辅助人格调用。
- 按实际出站顺序展示最终提示内容、角色、工具定义及影响上下文理解的请求信息。
- 将最终请求中的每个提示段关联到配置文件、提示词文件、记忆数据文件及稳定记录标识；没有文件来源的运行时内容必须如实标识来源类型。
- 以基础类 TUI 的分组、缩进和颜色区分不同提示段、来源类别与调用；在不支持颜色时提供等价的文本标识。
- 在请求发出前分别显示输入上下文用量估算、最大输出预留、预计峰值总占用、容量占比与剩余空间，并在提供商返回实际用量时显示对照结果。
- 每次最终提示构建完成后由类 TUI 完整展示并等待用户明确批准；批准后立即关闭并清除正文 TUI，只把已批准的不可变发送载荷交给 sender，`send_once` 无论成功或失败都在结束时释放该载荷。
- 维护者拒绝任一待批请求时，无痕撤销整个当前轮次并恢复到该轮输入提交前的应用状态，使本轮不进入后续记忆、恢复或上下文。
- 将普通 provider/网络失败与维护者明确拒绝分开处理：普通失败保留一条既有 USER pending 供恢复，明确拒绝不形成 pending。
- 当前工具保持只读；未来写工具只有具备可恢复事务或补偿契约时才能在可拒绝轮次中执行。
- 在调试模式下保证追踪完整性、凭据保护和不改变实际模型请求。

### Out of Scope

- 桌面图形化或远程调试控制台、多人共享追踪、浏览器界面及移动端界面。
- 修改、重排、重放或重新发送调试视图中的提示内容。
- 默认持久保存、导出或上传原始提示词追踪。
- 展示网络认证头、模型服务密钥、工具凭据或其他传输层秘密。
- 对启用调试之前的历史模型请求进行追溯重建。
- 模型费用预测、响应质量评分及性能分析面板。

## Clarifications

### Session 2026-07-19

- Q: 调试视图应通过哪种方式启停？ → A: 仅通过启动参数启用，退出程序后自动关闭。
- Q: 上下文窗口占用采用什么口径？ → A: 分别显示输入估算、最大输出预留和预计峰值总占用。
- Q: 调试追踪在应用内存中保留多久？ → A: 展示至批准；批准后、网络发送前立即从 TUI 清除正文与来源，sender 只保留同一不可变发送载荷并在 `send_once` 的 `finally` 中释放。
- Q: 调试模式下何时发送模型请求？ → A: 使用基础类 TUI 完整展示构建结果并等待用户批准；批准后先关闭并清除正文 TUI，再发送同一不可变载荷。
- Q: 用户拒绝发送时如何处理当前轮次？ → A: 无痕撤销整个当前轮次并返回输入界面；本轮视为从未存在，不对之后产生任何影响。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 检查最终提示词及来源 (Priority: P1)

维护者开启调试视图并发送一条消息后，可以在基础类 TUI 中立即看到等待批准的完整最终提示内容。最终请求被拆分为有序片段，每个片段在同一区域显示来源文件或明确的运行时来源，因此维护者能判断人格、状态、长短期记忆、当前输入和工具结果为何出现在本轮请求中，并决定是否允许发送。

**Why this priority**: 精确看到“最终发送了什么”和“每一段从哪里来”是该调试工具的核心价值，其他视觉和容量信息都建立在这项能力之上。

**Independent Test**: 使用带唯一标记的多份人格、提示模板、长期记忆、短期记录和当前输入发起一轮交互，核对调试视图中的最终顺序、正文和来源与实际出站请求及源文件完全对应。

**Acceptance Scenarios**:

1. **Given** 调试视图已开启且一轮聊天即将调用模型，**When** 最终出站请求构建完成，**Then** 类 TUI 在网络发送前显示该请求的全部提示承载字段、原始顺序和完整正文，并等待维护者明确批准。
2. **Given** 最终请求包含来自人格或提示模板文件的片段，**When** 维护者查看任一片段，**Then** 同一区域显示可定位的项目相对文件路径、配置修订和片段标识。
3. **Given** 最终请求包含长期记忆或短期原始记录，**When** 维护者查看该片段，**Then** 视图显示对应数据文件以及一个或多个稳定记忆或记录标识。
4. **Given** 片段来自当前输入、工具结果或其他没有独立文件的运行时值，**When** 维护者查看来源，**Then** 视图明确标为运行时来源并说明产生者，不伪造文件路径。
5. **Given** 一个提示段由多个文件或记录共同形成，**When** 来源被展示，**Then** 所有参与构建的来源均可见并保持确定顺序。

### User Story 2 - 实时区分一轮中的多次模型调用 (Priority: P2)

一轮交互可能触发记忆整理、聊天生成、工具调用后的续接或重试。维护者可以按实际发生顺序逐个检查并批准彼此独立的调用，清楚区分调用目的、使用的人格、提供商、模型、尝试次数和结果状态，不会把多个请求混成一个提示词。

**Why this priority**: 只有完整覆盖并区分所有模型调用，调试信息才能解释真实运行行为，而不仅是常见的单次聊天路径。

**Independent Test**: 构造一轮会依次触发记忆整理、聊天、工具返回后续接和一次提供商重试的交互，核对每个实际出站请求都产生独立且有序的追踪条目。

**Acceptance Scenarios**:

1. **Given** 一轮交互只触发一次模型请求，**When** 请求构建完成，**Then** 视图显示带轮次、流程、人格、状态、用途、提供商和模型信息的单一调用条目。
2. **Given** 一轮交互触发多个模型请求，**When** 各请求依次发生，**Then** 每次调用按实际顺序独立进入类 TUI 批准界面并具有稳定调用序号；前一调用未经决定时不得展示或发送后一调用。
3. **Given** 一个已批准请求发送后提供商调用失败并需要重试，**When** 新尝试的最终请求构建完成，**Then** 该尝试作为新的批准项展示；此前原始提示不恢复，失败状态与后续尝试不会被覆盖或合并。
4. **Given** 终端支持颜色，**When** 多个来源类别和调用同时展示，**Then** 它们使用稳定的颜色、分组和缩进错开展示；颜色关闭或不可用时，文本标签和边界仍能无歧义地区分内容。

### User Story 3 - 判断上下文窗口占用 (Priority: P3)

维护者在请求发出前即可分别看到本次请求预计使用的输入上下文量、允许生成的最大输出预留、两者形成的预计峰值总占用、模型上下文容量、占用比例和预计剩余空间，并能查看各提示段的输入用量明细。提供商返回实际输入与输出用量时，维护者还能看到实际值及其与预估值的差异。

**Why this priority**: 上下文占用解释了提示裁剪、容量不足和成本异常等常见问题，但它依赖前两个故事提供的准确请求边界和片段划分。

**Independent Test**: 使用空白、中文、英文、混合文本、长记忆和工具定义等代表性请求，核对总估算等于片段明细之和，并与提供商返回的实际输入用量比较。

**Acceptance Scenarios**:

1. **Given** 当前模型的上下文容量和最大输出限制已知，**When** 最终请求构建完成，**Then** 视图在请求结果返回前分别显示预计输入用量、最大输出预留、预计峰值总占用、峰值占用百分比、预计峰值剩余量和输入分段明细。
2. **Given** 当前模型的上下文容量未知，**When** 请求构建完成，**Then** 视图仍显示预计输入用量，但将容量、百分比和剩余量明确标为未知，不显示猜测值。
3. **Given** 提供商响应包含实际输入与输出用量，**When** 响应到达，**Then** 普通聊天输出在不重新打开 TUI 或恢复原始提示正文与来源的前提下显示该调用的实际输入、实际输出、实际总占用、估算误差和实际占用比例。
4. **Given** 估算能力不支持当前模型或请求内容，**When** 无法形成可信估算，**Then** 视图明确显示不可估算及原因，且不得以字符数冒充精确 token 数。

---

### User Story 4 - 安全启停调试视图 (Priority: P4)

维护者可以用简单、明确的方式开启或关闭调试视图。开启时，界面提示原始提示词可能包含私人记忆；关闭时，普通聊天行为、模型请求和默认输出均保持不变，系统也不会暗中保存原始追踪。

**Why this priority**: 原始提示词包含高敏感度的用户数据，调试能力必须保持显式、局部和可控，不能意外成为新的日志泄露面。

**Independent Test**: 对同一确定性输入分别在调试关闭和开启状态运行，比较实际出站请求，并检查屏幕、日志和磁盘中是否仅在开启时出现当前进程内的调试展示。

**Acceptance Scenarios**:

1. **Given** 启动时未提供调试参数，**When** 用户进行普通聊天，**Then** 不显示、记录或持久保存原始提示词追踪，实际模型请求保持既有行为。
2. **Given** 维护者通过启动参数开启调试视图，**When** 首次发起交互，**Then** 界面清晰标识调试已开启并提醒原始提示可能包含私人记忆。
3. **Given** 调试视图在当前运行中已开启，**When** 程序退出后再次正常启动，**Then** 调试视图恢复为关闭状态，且不需要额外执行关闭操作。
4. **Given** 调试视图已开启，**When** 追踪组件无法完整捕获或归因最终请求，**Then** 系统在发送该请求前停止受影响调用并给出安全、可操作的错误，而不是发送未被追踪的请求。
5. **Given** 最终请求或传输信息可能包含可用凭据，**When** 安全检查发现风险，**Then** 凭据不会出现在调试视图、日志或持久文件中，受影响请求不会被发送。
6. **Given** 等待批准的原始提示构建正在展示，**When** 维护者批准，**Then** 类 TUI 在网络发送前立即关闭并移除原始提示正文与来源，sender 仅持有同一个不可变发送载荷并在 `send_once` 成功或失败后的 `finally` 中释放，后续状态和实际用量不得使原文重新出现。
7. **Given** 任一模型请求正在等待批准，**When** 维护者拒绝发送，**Then** 当前请求不发送，整个当前轮次产生的输入、临时结果、记忆或索引候选、待恢复标记和调试数据均被撤销，应用恢复到提交该轮输入之前并直接返回输入界面。
8. **Given** 一个被拒绝并撤销的轮次，**When** 用户继续聊天、重启程序或触发记忆整理，**Then** 后续上下文、持久记录、来源索引、恢复状态和模型调用均不存在该轮留下的内容或标记。
9. **Given** 已批准请求遭遇普通 provider 或网络失败且重试已结束，**When** 当前轮收敛，**Then** 系统只发布一条 USER pending；下一次默认启动或显式 `--discard-pending` 必须只丢弃该尾部 pending 后进入新输入，只有显式 `--resume-pending` 才能恢复并重发；若是维护者明确拒绝，则不得形成 pending。
10. **Given** 当前工具注册表仅含只读工具，**When** 工具在可拒绝轮次中执行，**Then** 其结果只进入当前工作集；未来写工具若没有可恢复的 `prepare/commit/rollback` 或明确补偿契约，必须在任何副作用前被拒绝。

### Edge Cases

- 可选提示段为空、仅包含空白或被预算选择规则排除时，视图必须区分“空片段”“未参与最终请求”和“追踪缺失”。
- 多个文件包含相同正文时，来源必须依据实际加载关系而不是文本猜测来标注。
- 同一片段关联数百条原始记忆记录时，界面必须保持总来源数可见，并允许查看全部来源而不将其误报为单一文件。
- 配置或记忆文件在请求构建后被修改时，追踪必须指向构建本次请求时使用的配置修订和内容身份，不能把后来内容显示为本次来源。
- 多行文本、超长文本、简体中文、其他 Unicode 字符、控制字符及看似终端样式的内容不得破坏片段边界或伪造调试标签。
- 工具定义、工具结果、提供商重试和未来辅助人格调用必须采用与普通聊天调用相同的追踪契约。
- 交互式 TTY 不支持颜色或用户禁用颜色时，所有信息仍须通过明确文本标签和分隔符读取；stdin/stdout 非 TTY 或输出重定向时必须按 FR-027 在任何持久化和模型发送前失败。
- 已知上下文容量小于估算用量时，必须突出容量超限状态；不能仅显示超过 100% 的数字而不解释风险。
- 提供商没有返回实际用量或返回无效用量时，估算值必须继续明确标识为估算，不能升级为实际值。
- 调试展示自身失败时，不得泄露凭据、写入半份持久追踪或静默改变原始模型请求。
- 长时间运行或连续发生大量模型调用时，应用不得累积已发送请求的原始提示正文；每个已发送请求都必须从类 TUI 清除并从调试器内存释放。
- 调试参数在非交互终端中启用时，系统必须在构建或发送任何模型请求前给出可操作错误，不得退化为无法批准的普通文本输出。
- 当前轮在拒绝前已完成一个或多个经批准的辅助模型调用而尚未完成整轮时，系统必须丢弃这些响应及其所有本地派生结果并恢复轮前状态；已经发生的外部调用无法撤回，但不得再影响应用后续行为。
- 无痕撤销期间发生中断或局部清理失败时，系统必须在恢复后继续回滚到轮前检查点，且不得把该轮暴露为待恢复、已取消或普通历史记录。
- 已批准请求的普通 provider/网络失败必须收敛为一条可恢复 USER pending；该恢复语义不得被维护者明确拒绝复用。
- raw archive 中只有位于最末尾、没有对应 ASSISTANT 且未被长期记忆或 coverage 引用的单条 USER 才是可放弃 pending；历史中间 USER、完整轮次、身份或 hash 冲突一律失败关闭且不得修改文件。
- 默认启动和 `--discard-pending` 在没有 pending 时必须直接进入新输入；`--resume-pending` 没有 pending 时同样进入新输入，但不得把其他历史记录当作恢复目标。
- 写工具没有可恢复事务或补偿能力、能力声明与实现不一致或 prepare 失败时，副作用调用次数必须为 0。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 仅允许通过聊天程序的启动参数为当前运行启用调试视图；未提供参数时默认关闭，程序退出后启用状态 MUST 自动失效，且运行中 MUST NOT 切换或持久保存该状态。
- **FR-002**: 调试视图启用时，系统 MUST 为一轮交互触发的每一次模型提供商调用建立独立追踪，覆盖聊天、记忆整理、工具续接、重试和采用同一调用边界的未来辅助人格。
- **FR-003**: 每条追踪 MUST 以实际即将发出的请求为准，在最终组装和提供商适配完成后、网络发送前捕获全部提示承载字段。
- **FR-004**: 追踪 MUST 保留实际出站请求中的消息角色、消息顺序、完整正文、工具定义及其他影响模型可见上下文的内容；认证信息和纯传输元数据 MUST 排除。
- **FR-005**: 每条追踪 MUST 显示所属轮次、流程、调用序号、调用用途、人格、Agent 状态、提供商、模型、配置修订、尝试序号和当前结果状态。
- **FR-006**: 最终请求 MUST 同时提供逐段视图；每个实际参与请求的提示段 MUST 具有稳定片段标识、顺序、信任类别、完整正文和来源归因。
- **FR-007**: 对文件支持的提示段，来源归因 MUST 显示可定位的项目相对文件路径、内容身份和本次请求使用的配置或数据修订。
- **FR-008**: 对来自多份文件或多条记录的聚合片段，来源归因 MUST 按确定顺序列出全部文件路径和稳定记录标识，并明确聚合关系。
- **FR-009**: 对当前用户输入、临时工具结果或其他没有独立文件的内容，来源归因 MUST 显示明确的运行时来源类型、产生者和关联标识，且 MUST NOT 伪造文件路径。
- **FR-010**: 视图 MUST 区分“参与最终请求”“构建过程中被排除”“内容为空”和“来源未知”四种状态；只有第一种计入实际出站请求及上下文用量。
- **FR-011**: 追踪 MUST 在请求构建完成后实时进入基础类 TUI；完整提示正文、来源和上下文估算全部 mounted 且通过展示就绪校验前，批准操作 MUST 不可用，对应模型请求 MUST NOT 发送。
- **FR-012**: 同一轮中的多个调用、工具续接、失败尝试和重试 MUST 按真实发生顺序逐个进入批准界面并显示为独立调用，不得覆盖、合并或重新排序；前一调用未经批准或拒绝时不得处理后一调用。
- **FR-013**: 基础类 TUI 在支持颜色的交互终端中 SHOULD 为不同来源类别和调用使用稳定且可辨识的颜色，并 MUST 使用标题、边界和缩进错开展示各段。
- **FR-014**: 在交互式 TTY 中颜色不可用或被关闭时，系统 MUST 自动或按设置使用无颜色模式，并通过等价文本标签保持全部含义和边界；stdin/stdout 非 TTY 或输出重定向不属于无色降级，MUST 按 FR-027 失败。
- **FR-015**: 每次请求发送前，视图 MUST 分别显示预计输入 token 数及逐段估算、当前请求的最大输出 token 预留、两者之和形成的预计峰值总占用、已知的模型上下文容量、峰值占用百分比和预计峰值剩余 token 数；输入总估算 MUST 与参与请求的分段估算一致。
- **FR-016**: 上下文容量或可信估算不可用时，系统 MUST 显示“未知”或“不可估算”及原因，MUST NOT 生成无依据的容量、比例或精确度声明。
- **FR-017**: 提供商返回有效实际输入与输出用量时，系统 MUST 通过普通聊天输出显示对应调用的实际输入、实际输出、实际总占用、实际占用比例和输入估算误差；该结果可以引用发送前的数值摘要，但 MUST NOT 重新打开 TUI、恢复或继续保留原始提示正文与来源数据。
- **FR-018**: 当预计峰值总占用超过已知上下文容量或进入预先定义的高占用区间时，视图 MUST 给出醒目的分级状态，并分别说明输入主要占用片段与最大输出预留的贡献。
- **FR-019**: 调试视图启用后，原始提示构建只能在对应请求等待批准期间存在于基础类 TUI 和调试器必要的进程内状态中；维护者批准后 TUI MUST 在网络发送前立即关闭并清除正文与来源，presenter MUST 释放对应引用。此后 sender 只能保留同一份已批准的不可变发送载荷，并 MUST 在 `send_once` 成功或失败后的 `finally` 中释放；系统 MUST NOT 默认把原始提示正文写入日志、记忆、配置、追踪文件或其他持久介质。
- **FR-020**: 调试视图关闭时，系统 MUST 不产生原始提示展示或持久追踪，且相同输入、状态与配置形成的实际模型请求 MUST 与启用调试时一致。
- **FR-021**: 调试追踪 MUST 为只读观察能力，不得修改、删减、转义后替换或重新组织实际发送给模型的请求内容。
- **FR-022**: 调试模式下若任一实际出站调用无法在发送前完整捕获、形成逐段来源、通过追踪完整性校验或完整呈现批准界面，系统 MUST 阻止该调用并返回可操作错误。
- **FR-023**: 原始提示内容可能包含私人记忆；系统 MUST 在首次启用及每次新运行中提供清晰可见的本地暴露提醒，但不得用该提醒替代凭据保护。
- **FR-024**: 新增模型提供商、人格角色或工具续接流程时，MUST 能沿用同一追踪、来源、顺序、估算和错误语义，不得建立不可观察的提供商调用旁路。
- **FR-025**: 调试视图的颜色策略、高占用阈值和模型上下文容量元数据 MUST 可通过统一配置维护；缺失或无效配置 MUST 产生可操作错误或采用有文档说明的安全默认值，调试启用状态不得由该配置持久保存。
- **FR-026**: 调试模式 MUST 要求维护者对每个最终模型请求逐次作出明确批准；批准 MUST 绑定当前 call、attempt 和唯一物化发送载荷摘要，批准前不得发送，批准后发送的请求 MUST 与已展示内容一致，且批准动作不得修改请求。
- **FR-027**: 调试模式 MUST 依赖 stdin/stdout 均为 TTY 的可交互终端批准能力；任一非 TTY、输出重定向或该能力不可用时 MUST 在任何持久化和模型发送前失败，不得自动批准、普通打印提示正文或退化为无批准流程。
- **FR-028**: 维护者拒绝任一待批模型请求时，系统 MUST 不发送该请求并无痕撤销整个当前轮次，恢复到提交该轮用户输入之前的应用状态后返回输入界面。
- **FR-029**: 无痕撤销 MUST 原子移除或放弃本轮产生的用户输入、Agent 或辅助人格临时输出、工具结果、记忆与来源索引候选、状态变更、待恢复标记、上下文摘要、用量摘要和调试数据；MUST NOT 留下已取消记录、墓碑或任何可进入后续上下文的表示。
- **FR-030**: 若本轮在拒绝前已有经批准的辅助请求发送，系统 MUST 丢弃其响应及所有尚未完成整轮确认的本地派生结果；已发生的外部调用不可撤回，但其结果 MUST NOT 影响后续记忆、状态、工具或模型请求。
- **FR-031**: 无痕撤销在中断或局部失败后 MUST 可恢复并最终回到轮前检查点；在回滚完成前系统 MUST 阻止新轮次及任何模型请求，不得把被拒绝轮次转为待恢复轮次。
- **FR-032**: 已批准请求发生普通 provider 或网络失败且不再重试时，系统 MUST 将当前事务持久转换为 `READY_PENDING`，幂等发布且仅发布一条 USER pending；只有显式 `--resume-pending` 才允许恢复并重发该内容，下一次未指定恢复参数的默认启动或显式 `--discard-pending` MUST 原子丢弃该合法尾部 pending 后进入新输入；维护者明确拒绝 MUST NOT 形成 pending。
- **FR-033**: 当前工具注册表 MUST 只声明并执行只读工具；未来具有写副作用的工具在可拒绝轮次中 MUST 提供可持久恢复的 `prepare/commit/rollback` 或明确补偿契约，否则系统 MUST 在任何副作用发生前拒绝执行。
- **FR-034**: chat 与 memory curator profile MUST 从 `deepseek-chat` 迁移到 `deepseek-v4-flash`，保持 `thinking_enabled=false`、`max_output_tokens=8192` 及各 profile 现有 temperature、tools、structured-output 等生成参数不变；每个初始、重试和工具续接请求 MUST 在唯一物化载荷中显式发送 `thinking.type=disabled`，不得依赖 V4 默认思考模式；provider 能力元数据 MUST 记录 1,000,000 token context 和 384,000 token 输出上限。
- **FR-035**: `chat` MUST 提供互斥的 `--resume-pending` 与 `--discard-pending`；`start.ps1` MUST 提供互斥的 `-ResumePending` 与 `-DiscardPending`，且两者均可与 `-DebugPrompts` 组合。无 pending 时三种启动模式均 MUST 安全进入新输入，不得调用恢复发送。
- **FR-036**: pending 丢弃 MUST 只允许删除 raw archive 最末尾、角色为 USER、无对应 ASSISTANT 且未进入长期记忆、来源索引、coverage 或 curation frontier 的未完成轮次；MUST 保持此前完整轮次、全局 sequence 连续性、分段 JSONL、内容哈希和其他用户数据不变，并使用现有 WriterLease、私有权限与原子替换机制使崩溃后只可能保留完整旧状态或完整新状态。
- **FR-037**: fresh 调试轮次的 R、Esc、拒绝按钮和 Ctrl+C MUST 丢弃 PREPARED；恢复既有 pending 的调试轮次遇到相同明确拒绝时 MUST 通过受保护的尾部丢弃删除 raw pending。R、Esc 和拒绝按钮返回输入界面，Ctrl+C 完成丢弃后 MUST 以 130 退出；EOF、终端丢失或 presentation failure MUST 保持零发送且不得伪装成批准。
- **FR-038**: 等待批准的 TUI MUST 提供“复制框内全部内容”按钮和 `C` 快捷键，把最终 provider 载荷、全部提示片段及来源按当前安全可见文本完整复制到终端剪贴板；复制 MUST NOT 批准、拒绝、发送、关闭界面、改变请求或在应用内创建持久 trace，完成通知 MUST NOT 回显正文。
- **FR-039**: provider 适配器 MUST 按受控状态分类错误并关闭 SDK 内部隐藏重试；只有网络连接/超时及配置列出的 HTTP 429、500、503 可进入网关新 attempt 并重新审批，HTTP 400、401、402、403、422 与未知本地异常 MUST 在一次审批/发送后立即脱敏失败，不得重复弹出同一必败审批。
- **FR-040**: 工具调用续接 MUST 在所有 tool result 之前按原顺序回放产生调用的 assistant 消息及完整 `tool_calls` 身份、函数名和参数；非思考模式不得要求或持久化 `reasoning_content`，续接的 assistant/tool_calls 与 tool result 均 MUST 进入唯一物化、来源校验和独立审批。
- **FR-041**: 深度不可变的 `MaterializedSendPayload.sdk_kwargs` 在审批、摘要和 digest 校验期间 MUST 保持冻结；`send_once()` MUST 仅在真实 SDK 调用边界把同一 JSON 值无损还原为原生 dict/list/scalar 后编码，不得把 `mappingproxy`、tuple 等内部冻结容器直接交给 SDK，也不得在还原时改变字段、顺序语义或值。

### Core Business Rules *(mandatory)*

- **BR-001 — 出站请求真实性**: 正常情况下，调试视图中的最终请求必须与提供商实际接收的提示承载内容、角色和顺序一致；空内容、Unicode、多行内容和工具定义属于必须保持的边界；调试模式下若无法证明一致，调用必须在发送前失败。
- **BR-002 — 来源归因完整**: 正常情况下，每个最终提示段必须关联实际文件和内容身份；多来源聚合及无文件的运行时内容必须分别列出全部来源或明确运行时产生者；任何“来源未知”的参与片段均视为完整性失败并阻止发送。
- **BR-003 — 调用覆盖与批准无缺口**: 正常情况下，一轮中的每个模型调用都必须产生且只产生一个独立批准项；工具续接、辅助人格和重试是独立调用边界且必须逐次批准；出现漏记、重复、覆盖、顺序不一致或未经批准时，受影响调用不得发送。
- **BR-004 — 上下文估算诚实性**: 可用时必须分别显示请求前输入估算及其分段构成、最大输出预留和预计峰值总占用，并以已知容量计算峰值占用；容量未知、实际用量缺失和不支持的模型属于合法边界；无法可信估算时必须报告未知，不得把猜测表示为精确值，也不得用仅输入占用替代峰值总占用。
- **BR-005 — 视觉表达不承载唯一语义**: 支持颜色时应使用稳定色彩并配合分组缩进；颜色关闭、不可用或不可辨识时是必须支持的边界；任何视觉降级都必须保留文本标签、顺序和来源，不能使信息只能靠颜色理解。
- **BR-006 — 调试批准不改变请求**: 启用调试只增加发送前观察与批准门禁，不得修改模型请求、记忆、人格、工具行为或既定调用顺序；关闭调试是必须保持既有行为的边界；展示或批准失败时不得静默改写请求、自动批准或把半份追踪当作完整结果。
- **BR-007 — 本地临时暴露与凭据零泄露**: 正常原始提示只在显式启用的基础类 TUI 中展示至批准时点；批准后、网络发送前界面必须关闭并清除，presenter 必须释放正文与来源且不得持久化，sender 只持有同一不可变载荷并在 `send_once` 的 `finally` 中释放。私人记忆可在提醒后按原文展示，但认证信息绝不属于提示追踪；发现疑似可用凭据时必须阻止显示、持久化和出站请求，并返回脱敏错误。
- **BR-008 — 拒绝即无痕撤销**: 正常批准路径在发送前保持当前轮可确认且请求与展示一致；拒绝任一待批请求时，整个当前轮必须原子恢复到轮前检查点且当前请求发送次数为零；边界覆盖此前已批准辅助调用的本地结果丢弃，失败路径覆盖中断后继续回滚，最终不得留下可影响后续行为的记录、状态或恢复标记。
- **BR-009 — 普通失败保留但不默认阻塞**: 已批准请求发生普通 provider 或网络失败且重试结束时，当前轮必须通过 `READY_PENDING` 只发布一条 USER pending；显式 `--resume-pending` 保持可恢复性，默认启动与 `--discard-pending` 则只放弃该未完成尾部轮次并继续新对话。维护者明确拒绝是不同领域结果，必须撤销 fresh PREPARED 或删除 resumed pending。
- **BR-010 — 写工具副作用能力门禁**: 当前只读工具可在可拒绝轮次中执行且结果仅进入工作集；未来写工具只有在可恢复 `prepare/commit/rollback` 或明确补偿契约完成验证后才能准备副作用，能力缺失、声明不实或 prepare 失败时副作用调用次数必须为零。
- **BR-011 — 完整归档不可变、未完成尾部可放弃**: 已完成 USER/ASSISTANT 轮次继续永久不可删除；唯一未配对的合法尾部 USER 是尚未完成的可放弃轮次，只能在全量结构、hash、长期引用和 expected turn 身份校验通过后原子截尾，任何任意 turn id 或历史中间删除请求都必须失败关闭。

### Sensitive Credentials *(include if applicable)*

- **CR-001**: 模型提供商密钥、认证头、工具凭据及其他可用凭据 MUST NOT 进入原始提示词、来源元数据、调试界面、日志、错误详情、测试夹具或持久追踪。
- **CR-002**: 传输请求中的认证信息 MUST 与提示承载内容严格分离，并 MUST NOT 因“显示原始请求”而被复制到调试数据。
- **CR-003**: 在提示捕获或发送前发现疑似可用凭据时，系统 MUST 阻止受影响调用，向用户显示不含原值的处置指引，并沿用项目既有安全事件门禁。
- **CR-004**: 调试视图和自动化测试 MUST 仅使用明确无效的占位符；仓库及全部可达历史中的可用凭据数量 MUST 保持为零。

### Key Entities *(include if feature involves data)*

- **模型调用追踪（Model Call Trace）**: 一次等待批准的模型提供商调用的临时只读表示，包含轮次、流程、调用目的、人格、状态、提供商、模型、尝试序号、请求状态、最终请求和上下文估算；只保留至维护者批准且请求发送，之后从类 TUI 清除并由调试器释放。
- **最终出站请求（Final Outbound Request）**: 完成全部组装和提供商适配后即将发送的提示承载内容，不包含认证信息和纯传输元数据。
- **提示段追踪（Prompt Segment Trace）**: 最终请求中的有序组成部分，包含片段标识、正文、信任类别、参与状态和一个或多个来源引用。
- **来源引用（Prompt Source Reference）**: 指向配置或数据文件、内容身份、配置或数据修订、稳定记录标识的可定位关系；对无文件内容则记录运行时来源类型、产生者和关联标识。
- **上下文用量快照（Context Usage Snapshot）**: 请求发送前形成的输入总量及分段估算、最大输出预留、预计峰值总占用、已知容量、峰值占用比例、峰值剩余量和风险状态，以及响应后可选追加的实际输入、实际输出、实际总占用与估算误差。
- **调试展示策略（Debug Presentation Policy）**: 决定颜色和无颜色表现、高占用阈值、私人内容提醒以及类 TUI 批准后、网络发送前清除行为的可维护设置；调试启用状态仅由当前运行的启动参数决定。
- **轮前检查点（Pre-turn Checkpoint）**: 调试模式接收当前用户输入前的应用可恢复状态，用于在任一待批请求被拒绝或撤销中断后原子恢复，并证明本轮未进入后续上下文。
- **发送批准决定（Send Approval Decision）**: 维护者针对单个最终模型请求作出的批准或拒绝；批准允许完全一致的请求发送，拒绝触发整个当前轮次无痕撤销且不留下持久表示。
- **物化发送载荷（Materialized Send Payload）**: `materialize_sdk_kwargs()` 唯一一次生成的深度不可变、无认证 SDK 参数及其摘要；TUI 展示与 sender 发送引用同一对象，批准后仅由 sender 暂存并在 `send_once` 结束时释放。
- **轮次事务日志（Turn Transaction Journal）**: 仅含恢复必需数据的私有临时状态，使用 `PREPARED`、`READY_PENDING`、`READY_TO_COMMIT` 分别表达拒绝可丢弃、普通失败发布单条 pending 和成功发布完整轮次。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在至少 200 次涵盖聊天、记忆整理、工具续接、辅助人格、失败和重试的模型调用测试中，100% 实际出站调用在发送前具有且仅具有一个独立批准项和一次明确批准，顺序与实际调用顺序一致；未经批准的出站调用数量为 0。
- **SC-002**: 对代表性验收请求逐字段比较时，调试视图中的角色、顺序、正文和工具定义与实际提供商收到的提示承载内容 100% 一致；差异数量为 0。
- **SC-003**: 100% 参与最终请求的提示段都具有可定位文件来源或明确运行时来源；来源未知、错误文件归因和缺失聚合来源数量均为 0。
- **SC-004**: 在可用性验收中，至少 90% 的首次使用维护者能在 30 秒内从最终提示段定位到其来源文件或运行时产生者，并正确说明该段为何出现。
- **SC-005**: 在覆盖简体中文、英文、混合文本、长记忆和工具定义的参考请求集中，至少 95% 的请求前输入估算与提供商实际输入用量之差不超过实际值的 15% 或 128 tokens（二者取较大值）。
- **SC-006**: 对上下文容量和最大输出限制已知的请求，100% 正确显示输入估算、输入分段合计、最大输出预留、预计峰值总占用、峰值占用比例、峰值剩余量和超限状态；容量未知或实际用量缺失时，虚构数字数量为 0。
- **SC-007**: 在原生 Ubuntu 24.04、Python 3.13、80×24 `xterm-256color` 环境中，从 frozen request、来源和估算全部就绪到标题、调用身份和上下文摘要完成 mounted，30 次同一进程内启动的 p95 MUST 不超过 500 毫秒；首次冷启动单独记录且不纳入门禁，完整追踪展示并获得明确批准前 provider 收到的请求数量为 0。
- **SC-008**: 在支持颜色、禁用颜色和不支持颜色的交互式 TTY 验收环境中，100% 片段和调用都能仅凭文本标签、边界与顺序被无歧义识别；stdin/stdout 非 TTY 或重定向时在任何持久化和模型发送前失败，泄露的提示正文数量为 0。
- **SC-009**: 对同一确定性输入进行启用与关闭对照时，实际模型请求、记忆变更和工具行为差异数量为 0；关闭状态下原始提示调试输出和持久追踪数量均为 0。
- **SC-010**: 调试界面、日志、错误、测试制品、仓库和全部可达 Git 历史中的可用凭据数量为 0；调试原始提示被默认持久保存的数量为 0。
- **SC-011**: README、快速开始、配置和故障排查中的调试示例全部可按文档完成，且覆盖启用、观察、容量解释、无颜色降级、关闭和安全检查。
- **SC-012**: 在单次运行中连续批准并发送 1,000 次调试模型调用后，每个请求一经批准便在网络发送前从类 TUI 移除原始提示构建，presenter 遗留的正文和来源数据数量为 0，且每次 `send_once` 成功或失败后 sender 遗留的发送载荷数量为 0；实际用量摘要不会恢复原文。
- **SC-013**: 在分别于首个聊天请求、记忆整理后续请求、工具续接和重试批准点拒绝的验收测试中，当前被拒绝请求的提供商发送次数为 0；回滚后持久数据、状态、待恢复信息和下一轮模型上下文与提交被拒绝轮次输入之前的检查点 100% 一致。

## Assumptions

- 首版调试视图服务于本地单用户维护者，并以现有终端内的基础类 TUI 形式提供构建检查与逐次批准；桌面、浏览器或远程图形界面可在后续功能中考虑。
- 调试模式默认关闭且只能通过聊天程序的启动参数为当前运行显式开启；退出后自动关闭，不能在运行中切换，也不能由配置持久启用。
- “原始提示词”指完成最终组装和提供商适配后实际出站请求中的消息、工具定义及其他模型可见内容，不包括认证头、网络封装和模型不可见的内部对象。
- 一轮交互触发的聊天、记忆整理、工具结果续接、重试和未来辅助人格调用都属于“每次对话发给模型提供商”的观察范围。
- 静态人格和模板使用项目相对文件路径定位；长期与短期记忆使用数据文件路径及稳定记录标识定位；当前输入和临时工具结果没有独立文件时使用运行时来源标签。
- 上下文窗口容量来自当前模型的受维护元数据，最大输出预留采用本次实际请求限制；无法确认任一数值时允许显示未知，但不得静默使用其他模型或其他请求的数值。
- 提供商可能不返回实际 token 用量；这不会阻止请求前估算，但界面必须保持估算与实际值的语义区别。
- 原始提示可能包含私人记忆，维护者接受其在显式启用的本地界面中出现；该选择不包含任何凭据暴露或默认持久化授权。
- 类 TUI 只在请求等待批准期间展示并保留原始提示构建；维护者批准后、网络发送前，原文和来源立即从界面与 presenter 移除，sender 仅保留同一不可变发送载荷并在 `send_once` 的 `finally` 中释放；响应后的实际用量由普通聊天输出以不含原文的独立摘要展示。
- 调试模式中的当前轮数据在整轮确认前视为可无痕撤销的临时工作；拒绝任一待批请求会恢复轮前检查点并返回输入界面。此前已发送的外部辅助调用无法撤回，但其响应和本地派生结果不会进入之后的应用状态。
- 普通 provider/网络失败继续使用现有 USER pending；只有显式 `--resume-pending` 重发，默认启动和 `--discard-pending` 均放弃该未完成尾部轮次并开始新对话。
- `deepseek-v4-flash` 使用非思考模式；chat 与 memory curator 的 `max_output_tokens=8192` 及现有 temperature、tools、structured-output 设置保持不变，1M/384K 仅作为 provider 能力上限元数据。
- 原生 Linux 是主要支持平台，Windows 是次要功能兼容平台，macOS 不在本功能范围内。
